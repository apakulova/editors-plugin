# Аналитика плагина

Этот документ описывает всю действующую систему мониторинга плагина: как технические данные проходят из Figma в PostHog, что можно увидеть на дашбордах и как из этих данных собираются сообщения Telegram-бота.

Документ рассчитан одновременно:

- на автора плагина без технической подготовки;
- на разработчика или агента, который продолжит работу в следующем чате;
- на проверку того, что аналитика не вмешивается в работу типографа и не получает пользовательские тексты.

## Коротко: как устроен весь путь

1. Пользователь запускает «Чистовик» в Figma.
2. Плагин отмечает начало запуска и его общие параметры: режим, область запуска и включённые опции.
3. После обработки плагин отправляет один из двух результатов: успешное завершение или ошибку.
4. Сначала события приходят на служебный адрес «Чистовика» на Vercel.
5. Vercel проверяет событие и надёжно сохраняет его во временную очередь.
6. Отдельный обработчик Vercel пересылает событие из очереди в PostHog Cloud EU и повторяет попытки при сбое.
7. PostHog постоянно хранит события и строит по ним графики.
8. Vercel по расписанию или по команде Telegram запрашивает у PostHog готовые суммы.
9. Telegram-бот превращает числа в понятную русскую сводку.

PostHog и Telegram не управляют плагином. Если интернет, PostHog, Vercel или Telegram недоступны, типограф всё равно должен обработать текст и показать обычное уведомление Figma.

## Что именно отправляется из Figma

Плагин отправляет не текст макета, а короткие технические записи — события. Например: «обработка началась», «обработка закончилась успешно», «произошла ошибка».

Действующие события:

| Техническое название | Что означает |
|---|---|
| `plugin_run_started` | Пользователь запустил типограф |
| `plugin_run_completed` | Обработка закончилась успешно |
| `plugin_run_failed` | Обработка закончилась ошибкой |
| `settings_opened` | Пользователь открыл окно продвинутых фич |
| `channel_link_clicked` | Пользователь перешёл по ссылке на канал |
| `website_link_clicked` | Пользователь перешёл по ссылке на сайт автора |

Один запуск типографа должен дать:

- одно событие `plugin_run_started`;
- затем ровно одно финальное событие: `plugin_run_completed` или `plugin_run_failed`.

Если событие начала есть, а финального события нет, в отчёте появляется запуск «без финального статуса». Это сигнал проверить, закрылся ли плагин раньше отправки события, потерялось ли событие в очереди или существует путь выполнения без финального результата.

## Как различаются пользователи и запуски

При первом запуске плагин создаёт случайный анонимный номер и хранит его в локальном хранилище Figma `figma.clientStorage`.

Этот номер:

- не содержит имя, email или Figma user id;
- нужен только для подсчёта уникальных пользователей;
- может измениться после очистки локальных данных, смены устройства или смены `plugin id`.

Для каждого отдельного запуска создаётся ещё один случайный номер — `run_id`. Одинаковый `run_id` записывается в событие начала и финальное событие, чтобы PostHog мог связать их между собой.

У каждого отдельного события есть ещё `uuid` — случайный технический номер в стандартном UUID-формате. Он не связан с пользователем. Номер создаётся один раз, сохраняется вместе с событием в локальной очереди и не меняется при повторной отправке. Поэтому, если PostHog уже принял событие, но плагин не получил подтверждение и отправил его ещё раз, PostHog распознаёт повтор, а не создаёт вторую запись.

## Общие сведения о запуске

События запуска содержат:

| Поле | Простое объяснение |
|---|---|
| `source` | Быстрый запуск или запуск из окна продвинутых фич |
| `mode` | Быстрый режим, «Для красоты» или «Для разработки» |
| `selection_scope` | Текстовый слой, фрейм или другой контейнер, вся страница либо мультивыбор |
| `selected_nodes_count` | Сколько объектов было выделено перед запуском |
| `selected_text_nodes_count` | Сколько из выделенных объектов были текстовыми слоями |
| `process_hidden_nodes` | Была ли включена обработка скрытых слоёв |
| `process_locked_nodes` | Была ли включена обработка слоёв с замочком |
| `recolor_existing_asterisks` | Была ли включена опция разбора одиночных звёздочек |
| `run_id` | Анонимный номер конкретного запуска |
| `plugin_release` | Дата опубликованной сборки плагина |
| `analytics_schema_version` | Версия набора аналитических полей |
| `performance_measurement_version` | Версия способа измерения времени |
| `point_editing_phase` | Текущий способ работы новой системы; `shadow` означает только проверку расчёта, `point_safe` — локальную точечную запись с обязательной проверкой оформления |

При сохранении и пересылке Vercel добавляет безопасные технические поля:

| Поле | Простое объяснение |
|---|---|
| `analytics_transport` | Каким путём событие дошло до PostHog; для новой схемы — `vercel_queue_v1` |
| `analytics_delivery_delay_ms` | Сколько времени прошло между созданием события в Figma и его приёмом на Vercel; помогает увидеть позднюю повторную отправку из очереди |
| `analytics_queue_wait_ms` | Сколько времени событие ожидало внутри очереди Vercel перед успешной отправкой в PostHog |
| `analytics_queue_delivery_count` | С какой попытки очередь смогла доставить событие в PostHog |

`plugin_release` записывается московской датой в формате `YYYY-MM-DD`. Если в один день публикуются две разные сборки, можно использовать суффикс `.1`, `.2`. Перед каждой публикацией нужно проверить константу `ANALYTICS_PLUGIN_RELEASE` в `src/code.ts`.

## Что добавляется после успешной обработки

`plugin_run_completed` содержит итоговые счётчики:

- сколько текстовых слоёв найдено;
- сколько обработано;
- сколько действительно изменено;
- сколько скрытых и заблокированных слоёв пропущено;
- сколько символов проверено;
- сколько символов было в изменённых слоях;
- длина самого большого текстового слоя;
- время самого медленного текстового слоя;
- сколько фрагментов с разным оформлением пришлось сохранить;
- сколько уникальных шрифтов пришлось загрузить;
- были ли попытки аварийно вернуть исходное состояние;
- удалось ли такое возвращение;
- для скольких изменяемых слоёв рассчитан точечный план;
- сколько точечных операций найдено и каков максимум для одного слоя;
- были ли несовпадения между старым результатом и новым планом;
- общее время запуска.

Отдельно измеряется время этапов:

| Поле PostHog | Название в отчётах | Что происходит на этом этапе |
|---|---|---|
| `timing_collect_text_ms` | Поиск текстовых слоёв | Поиск текста и проверка скрытых и заблокированных слоёв |
| `timing_typography_ms` | Применение правил типографики | Кавычки, тире, числа, телефоны, пробелы и остальные правила |
| `timing_point_edit_planning_ms` | Расчёт точечных изменений | Сравнение исходного и готового текста и подготовка списка небольших правок |
| `timing_fonts_ms` | Загрузка шрифтов | Ожидание Figma при подготовке нужных шрифтов |
| `timing_read_styles_ms` | Чтение оформления | Запоминание шрифтов, цветов, ссылок, списков и других свойств |
| `timing_compare_text_ms` | Сравнение текста | Сопоставление исходного и исправленного текста |
| `timing_write_text_ms` | Запись текста | Передача исправленного текста в Figma |
| `timing_restore_styles_ms` | Проверка оформления | В точечной версии — проверка сохранённых свойств после записи; в старой — возвращение оформления |
| `timing_development_markers_ms` | Работа со служебными звёздочками | Чтение, окрашивание и сохранение служебных `*` |
| `timing_other_ms` | Остальные операции | Время, которое не вошло в перечисленные этапы |

Измерения производительности считаются сопоставимыми только внутри одной версии поля `performance_measurement_version`. Подробные замеры правил опубликованной полной записи используют версию `3`. Теневой режим использовал версию `4`. Локальная точечная запись использует версию `5` и `point_editing_phase: point_safe`, потому что способ записи и смысл этапа проверки оформления изменились. Ежедневный отчёт продолжает считать опубликованную версию `3`, пока точечная сборка не готова к выпуску.

Новая система передаёт только числа:

| Поле PostHog | Простое объяснение |
|---|---|
| `point_edit_planned_layers_count` | Для скольких изменяемых слоёв рассчитан точечный план |
| `point_edit_operations_count` | Сколько вставок, удалений и замен получилось во всём запуске |
| `point_edit_max_operations_count` | Самое большое число операций в одном слое |
| `point_edit_mismatch_layers_count` | Для скольких слоёв применение плана к временной строке не дало старый итоговый текст; нормальное значение — `0` |

Текст пользователя, название слоя и название файла в этих полях не передаются. В теневом режиме несовпадение не влияло на старую запись. В точечном режиме несовпадение останавливает запись до изменения слоя либо запускает проверяемую штатную отмену Figma, если изменение уже началось.

### Что известно о конкретных правилах

В том же итоговом событии плагин передаёт сводку по всем 77 постоянным кодам из `docs/typography-rules.md`. Отдельных сетевых запросов для каждого правила нет.

| Поле PostHog | Простое объяснение |
|---|---|
| `rule_analytics_version` | Версия устройства подробных замеров правил; корректное подтверждение итоговых изменений начинается с версии `2` |
| `rule_changed_codes` | Коды правил, которые меняли промежуточный текст хотя бы в одном слое, чей окончательный текст действительно изменился |
| `rule_changed_codes_count` | Сколько разных правил изменило текст |
| `rule_metrics_json` | Сводка по каждому коду: число проверок, применений, изменённых слоёв и суммарное время |
| `rule_slowest_code` | Самое медленное правило этого запуска |
| `rule_slowest_duration_ms` | Сколько времени суммарно заняло самое медленное правило |
| `rule_most_active_code` | Правило, изменившее больше всего текстовых слоёв |
| `rule_most_active_changed_layers` | Сколько слоёв изменило самое активное правило |
| `rule_failed_code` | Код правила, внутри которого произошла техническая ошибка |
| `rule_change_pairs_json` | Какие самостоятельные правила последовательно меняли один текстовый слой |
| `rule_change_pairs_count` | Сколько разных последовательных пар встретилось |
| `rule_measured_codes_count` | Сколько постоянных кодов присутствует в сводке; для текущей версии должно быть `77` |

`rule_metrics_json` и `rule_change_pairs_json` содержат только коды, числа и время. Текста макета в них нет.

Время и число проверок правила записываются всегда. Применение правила, изменённый слой и последовательная пара записываются только после сравнения с окончательным состоянием слоя в Figma. Если окончательный текст слоя остался прежним, все временные внутренние изменения этого слоя отбрасываются. Точечная запись текста уже работает, но аналитика правил пока по-прежнему хранит итог только на уровне целого слоя: она не связывает конкретное правило с конкретной точечной операцией. Поэтому сочетания правил внутри одного реально изменившегося слоя остаются диагностической подсказкой, а не доказанным конфликтом.

Последовательная пара правил не считается доказанным конфликтом: правила могли изменить разные места одного слоя. Это диагностическая подсказка, какие сочетания стоит проверять в первую очередь. Для точного определения перезаписи одного и того же места понадобится отдельное сопоставление правил с рассчитанными точечными операциями; сейчас такого поля в аналитике нет.

## Что добавляется при ошибке

`plugin_run_failed` содержит:

- крупный этап, на котором остановилась обработка;
- понятную категорию причины;
- внутреннюю операцию;
- стабильное место в коде;
- техническое имя ошибки;
- короткий анонимный отпечаток ошибки;
- доступные к моменту ошибки счётчики слоёв, символов и времени;
- сведения о попытке отменить запуск через контрольную точку Figma и о результате проверки исходного текста, оформления и библиотечных связей.

Перед точечной записью шрифты загружаются через Figma API, а оформление запоминается без повторного открытия библиотечных стилей и переменных. Точечный режим не назначает эти связи заново: он оставляет их на месте и после записи сравнивает фактические идентификаторы и свойства с исходными. Отдельная проверка доступности стилей и переменных через Figma API остаётся только в старом режиме полной записи. Ожидание страницы, шрифта и главного компонента, а в старом режиме также стиля и переменной ограничено 15 секундами. После каждого ожидания плагин повторно сверяет текст и оформление: новый текст не перезаписывается, а изменившееся оформление перечитывается и проверяется заново. Если нужный ресурс недоступен, слой не изменяется, поэтому счётчик попыток аварийного возврата не увеличивается. Удалённый до записи слой безопасно пропускается и не считается ошибкой.

Контрольная точка Figma создаётся не в начале подготовки, а непосредственно перед первым изменением. Поэтому ручная правка другого слоя во время загрузки шрифтов не должна исчезнуть при отмене Чистовика. Если ошибка произошла уже после записи, одна штатная отмена Figma возвращает весь текущий запуск, включая слои, которые успели обработаться раньше. `rollback_failed` означает, что после этой отмены плагин всё равно не смог подтвердить исходное состояние.

После точечной записи плагин дополнительно проверяет фактические свойства каждого символа по рассчитанному плану. Это относится и к смешанным слоям с несколькими стилями. Также проверяются привязка текста к свойству компонента, цепочка родителей и связь каждого родительского экземпляра с тем же главным компонентом. Если Figma приняла команды без явной ошибки, но итоговое оформление или компонентная связь отличаются, запуск всё равно получает категорию `restore_styles_failed`, а затем отменяется штатным механизмом Figma.

Основные понятные категории:

| Код | Значение |
|---|---|
| `font_unavailable` | Недоступен шрифт |
| `layer_not_editable` | Слой нельзя изменить |
| `layer_changed` | Текст изменился во время подготовки записи или слой стал недоступен в ситуации, которую нельзя было безопасно пропустить |
| `mixed_or_unsupported_property` | Figma вернула смешанное или неподдерживаемое свойство |
| `write_text_failed` | Не удалось записать исправленный текст |
| `restore_styles_failed` | Не удалось вернуть оформление |
| `rollback_failed` | Не удалось вернуть исходное состояние после ошибки |
| `typography_failed` | Ошибка внутри правил типографики |
| `timeout` | Превышено время ожидания |
| `unknown` | Причину пока не удалось определить |

Более подробные расшифровки и ещё не реализованные варианты расширения хранятся в `docs/error-monitoring.md`.

## Что никогда не отправляется

В PostHog и Telegram нельзя отправлять:

- текст из макета;
- фрагменты текста;
- названия слоёв;
- названия файлов и страниц;
- названия компонентов;
- имена пользователей;
- email;
- Figma user id;
- полный stack trace, если в нём может оказаться лишний контекст.

В событиях принудительно используются:

- `$geoip_disable: true` — PostHog не должен добавлять город, страну и координаты;
- `$process_person_profile: false` — PostHog не должен создавать расширенный профиль человека.

## Как события доходят до PostHog

Плагин больше не обращается к PostHog напрямую. Он отправляет события на служебный адрес «Чистовика»:

```text
https://chistovik-plugin.vercel.app/api/capture
```

В `manifest.json` разрешён только домен:

```text
https://chistovik-plugin.vercel.app
```

Разрешать все домены через `"*"` нельзя.

Отправка устроена так:

1. Плагин создаёт событие.
2. Кладёт его в локальную очередь в `figma.clientStorage`.
3. Пытается отправить всю очередь на Vercel.
4. Vercel принимает только известные события «Чистовика», проверяет обязательные поля и ограничивает размер запроса.
5. Vercel сохраняет событие во временную очередь одновременно в нескольких зонах доступности. Повторная отправка того же `uuid` не создаёт вторую запись очереди.
6. Только после надёжного сохранения Vercel сообщает плагину об успехе.
7. Плагин удаляет принятое событие из своей локальной очереди.
8. Отдельный закрытый обработчик Vercel берёт событие из временной очереди и отправляет его в PostHog.
9. Если PostHog не подтвердил запись, обработчик завершает попытку с ошибкой, а Vercel автоматически повторяет доставку.
10. После подтверждения PostHog событие удаляется из временной очереди Vercel.

В локальной очереди Figma хранится не больше 100 последних событий. Если сама очередь Vercel недоступна и не подтвердила сохранение, событие остаётся в Figma до следующей попытки.

Очередь Vercel хранит событие только временно — максимум семь дней или до первого подтверждённого сохранения в PostHog. Постоянное аналитическое хранилище по-прежнему одно — PostHog. Если PostHog недоступен дольше семи дней подряд, оставшиеся события могут истечь; это предел выбранной временной очереди.

Vercel Queues пока имеет статус public beta. Очередь доступна на всех тарифах и оплачивается за операции; при текущем небольшом числе запусков стоимость должна быть минимальной. Состояние очереди, количество ожидающих сообщений и возраст самого старого сообщения можно смотреть в разделе Vercel `Observability → Queues`.

Аналитика работает отдельно от типографики:

- ошибки аналитики гаснут внутри аналитического слоя;
- пользователь не видит уведомлений об отправке аналитики;
- запуск из окна продвинутых фич не ждёт отправку;
- после завершения быстрого запуска финальное уведомление Figma остаётся видимым, а перед закрытием плагин дополнительно даёт очереди короткий период до 500 мс;
- сеть не должна задерживать изменение текста или финальное уведомление.

В очередь Vercel и PostHog Capture API передаётся техническое поле `uuid` в правильном UUID-формате. Оно защищает и очередь, и PostHog от повторной записи одного события. Если PostHog принял событие, но ответ потерялся, повторная доставка с тем же `uuid` не должна создать дубль. Старые записи локальной очереди с внутренними номерами вида `evt_...` при чтении получают постоянный совместимый UUID.

## Как данные попадают из PostHog в Telegram

Telegram-бот не получает события напрямую из Figma.

Схема такая:

1. Код на Vercel обращается к PostHog.
2. PostHog считает суммы за нужный период.
3. Vercel получает готовые числа.
4. Общий модуль `scripts/lib/analytics-report.js` превращает их в русский текст.
5. Vercel отправляет текст через Telegram Bot API.

Это означает, что:

- Figma-плагин не знает Telegram-токен;
- Telegram-бот не получает пользовательский текст из Figma;
- изменения Telegram-отчётов обычно требуют нового деплоя Vercel, но не обновления плагина в Figma;
- новые поля появятся в отчётах только после публикации версии плагина, которая начала их отправлять.

Telegram-бот по-прежнему считает данные только после их появления в PostHog. Он не складывает результаты PostHog с временной очередью Vercel, чтобы не получить двойные или неполные числа. Если событие дошло до PostHog с задержкой, последующие команды бота увидят его с исходным временем события. Уже отправленная ежедневная сводка автоматически задним числом не исправляется.

## Ежедневная сводка

Vercel Cron ежедневно вызывает:

```text
https://chistovik-plugin.vercel.app/api/daily-analytics
```

Расписание в `vercel.json` — `06:00 UTC`, то есть около `09:00` по Москве. На тарифе Vercel Hobby запуск может произойти не ровно в указанную минуту, а в пределах часа.

Ежедневное сообщение собирается за предыдущий полностью завершённый календарный день по Москве.

До начала перехода на точечную обработку сразу после заголовка временно показывался отдельный абзац о готовности. В режиме `baseline` использовались два согласованных варианта:

```text
🛑 Нельзя делать доработки — ещё не накопились 7 полных дней или 30 успешных обработок
```

Когда выполнены оба условия, текст автоматически меняется на:

```text
✅ Можно приступать к переходу на точечную обработку текста
```

В абзаце не показывались текущие счётчики. После начала первых изменений точечной обработки 5 августа 2026 года этап переключён с `baseline` на `implementation`. Поэтому ежедневное сообщение и команда `/today` больше не показывают ни красный, ни зелёный временный абзац.

В сводке показываются:

- запуски типографа;
- уникальные пользователи;
- успешные обработки и их доля;
- запуски без финального статуса;
- количество ошибок;
- количество пользователей, столкнувшихся с ошибкой;
- доля запусков с ошибками;
- до двух самых частых известных причин;
- обычное время обработки;
- время, в которое уложились 90% обработок;
- режимы;
- область запуска;
- включённые опции;
- открытия настроек;
- переходы в канал.

Выводы с `📍` сравнивают день с предыдущими семью днями:

- количество запусков — со средним числом запусков в день;
- долю ошибок — со средней долей ошибок;
- скорость — с обычным временем обработки.

Изменение меньше 10% считается примерно одинаковым. Для текстовой оценки скорости изменение от 10% до 25% считается небольшим, больше 25% — заметным.

Если нет чисел производительности, весь блок производительности пропускается. Время для 90% обработок показывается только при наличии не менее 10 подходящих успешных запусков.

Если за день не было запусков, основная часть сводки сокращается до:

```text
Плагин никто не запускал
```

Помимо этого текста сохраняется временный абзац о готовности к точечной обработке и ссылка на общий дашборд.

Если PostHog вернул непонятный или неполный ответ, бот не подставляет ложные нули. Он отправляет сообщение:

```text
🛑 Не удалось собрать отчёт за <дата>

PostHog вернул неожиданный формат данных.
```

## Действующие команды Telegram

### `/today`

Отправляет общую сводку за текущий, ещё не завершённый день по Москве. Структура совпадает с ежедневной сводкой за вчера.

### `/speed`

Отправляет отчёт по скорости за семь полностью завершённых дней и сравнивает их с предыдущими семью днями.

Отчёт показывает:

- количество успешных обработок;
- среднее время;
- время, в которое уложились 90% обработок;
- самый медленный запуск;
- все ненулевые этапы обработки;
- самый долгий известный этап;
- изменение скорости относительно предыдущей недели.

Если подходящих успешных запусков меньше 10, бот пишет, что данных пока слишком мало для оценки.

### `/errors`

Отправляет отчёт по ошибкам за семь полностью завершённых дней и сравнивает их с предыдущими семью днями.

Отчёт показывает:

- все запуски типографа;
- количество ошибок;
- количество пострадавших пользователей;
- долю запусков с ошибкой;
- все известные ненулевые причины;
- все известные ненулевые области запуска;
- изменение доли ошибок;
- самую частую причину или несколько причин с одинаковым максимальным числом ошибок.

Если ошибок не было, бот пишет:

```text
За последние 7 дней ошибок не было
```

В меню Telegram используются подписи:

```text
/today — Отчёт за сегодня
/speed — Отчёт по скорости за 7 дней
/errors — Отчёт по ошибкам за 7 дней
```

Другие команды сейчас не запланированы.

## Как считаются основные показатели

### Запуски типографа

Количество уникальных `run_id` среди событий `plugin_run_started`. Если одно событие случайно дошло до PostHog дважды, запуск всё равно считается один раз.

### Успешные обработки

Количество уникальных `run_id` среди событий `plugin_run_completed`.

### Ошибки

Количество уникальных `run_id` среди событий `plugin_run_failed`.

### Без финального статуса

```text
начала − успешные завершения − ошибки
```

Значение не может быть меньше нуля.

Режимы, области запуска и включённые опции также считаются по уникальным `run_id`, а не по числу сырых записей. Причины и области ошибок группируются тем же способом.

Показатели скорости сначала объединяют повторные записи с одинаковым `run_id` и только потом считают обычное время, 90-й процентиль, среднее, самый медленный запуск и разбивку по этапам. Один повторно доставленный результат не должен получать дополнительный вес.

В графиках PostHog используется совместимая формула: если у события есть `run_id`, считается он; для старых событий без `run_id` используется собственный номер записи PostHog. Поэтому защита от дублей не обнуляет раннюю историю дашборда.

### Доля успешных обработок

```text
успешные завершения / (успешные завершения + ошибки)
```

Запуски без финального статуса в этот процент не входят.

### Доля запусков с ошибкой

```text
ошибки / все начала запуска
```

### Уникальные пользователи

Количество разных анонимных `distinct_id` среди событий начала запуска.

### Обычное время

Медиана: половина подходящих запусков была быстрее этого значения, половина — медленнее. В ежедневном отчёте это называется «обычное время обработки».

### 90% обработок

Значение, быстрее которого завершились 90% подходящих запусков. Оно лучше среднего показывает, насколько долго приходится ждать в большинстве случаев.

## Где находится код

### Внутри Figma-плагина

- `src/code.ts` — сбор событий, анонимный id, очередь и отправка на Vercel;
- `manifest.json` — разрешённый домен Vercel;
- `dist/code.js` — собранная версия плагина.

### Пересылка, отчёты и Telegram

- `api/capture.js` — доступная для Figma точка приёма событий;
- `api/queues/posthog.js` — закрытый обработчик очереди, который доставляет события в PostHog;
- `scripts/lib/analytics-capture.js` — проверка событий, сохранение в очередь и пересылка в PostHog;
- `scripts/lib/analytics-report.js` — запросы к PostHog, расчёты, выводы и тексты сообщений;
- `api/daily-analytics.js` — ежедневный отчёт за вчера;
- `api/telegram.js` — обработка команд `/today`, `/speed` и `/errors`;
- `scripts/send-daily-analytics.js` — резервный ручной отчёт за вчера;
- `scripts/configure-telegram-menu.js` — обновление меню команд;
- `vercel.json` — расписание ежедневного отчёта и подключение закрытого обработчика к теме очереди `chistovik-analytics`;
- `.github/workflows/daily-analytics.yml` — ручной резервный запуск;
- `.github/workflows/configure-telegram-menu.yml` — безопасное обновление меню.

## Секреты и настройки

На Vercel должны быть заданы:

```text
POSTHOG_PERSONAL_API_KEY
POSTHOG_HOST=https://eu.posthog.com
POSTHOG_PROJECT_ID=184090
POSTHOG_DASHBOARD_URL=https://eu.posthog.com/project/184090/dashboard/695809
POSTHOG_PERFORMANCE_DASHBOARD_URL=https://eu.posthog.com/project/184090/dashboard/854930
TELEGRAM_BOT_TOKEN
TELEGRAM_CHAT_ID
TELEGRAM_WEBHOOK_SECRET
CRON_SECRET
```

Для приёма событий можно дополнительно задать `POSTHOG_PROJECT_TOKEN` и `POSTHOG_CAPTURE_URL`. Если их нет, используется закреплённый публичный токен проекта «Чистовика» и адрес PostHog Cloud EU. Персональный ключ `POSTHOG_PERSONAL_API_KEY` для чтения отчётов остаётся секретным и никогда не отправляется из Figma.

Vercel Queues получает доступ автоматически через служебный OIDC-токен Vercel. Отдельный секрет очереди в Environment Variables добавлять не нужно.

Для резервного запуска через GitHub Actions используются:

```text
POSTHOG_PERSONAL_API_KEY
TELEGRAM_BOT_TOKEN
TELEGRAM_CHAT_ID
```

Персональные ключи PostHog, Telegram-токен и остальные секреты нельзя хранить в репозитории, документации или сообщениях чата. Публичный `POSTHOG_PROJECT_TOKEN`, который разрешает только запись событий в конкретный проект, не является персональным ключом и может быть закреплён в коде пересылки.

### Как узнать `TELEGRAM_CHAT_ID`

1. Написать боту `/start`.
2. Временно удалить webhook, если `getUpdates` возвращает пустой результат.
3. Открыть:

```text
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getUpdates
```

4. Найти `message.chat.id`.
5. Сохранить это число в Vercel как `TELEGRAM_CHAT_ID`.

### Как создать секреты

Для `TELEGRAM_WEBHOOK_SECRET` и `CRON_SECRET` нужны две разные длинные случайные строки. Каждую можно создать командой:

```bash
openssl rand -hex 32
```

Значения сохраняются только в Vercel Environment Variables.

## Настройка Telegram webhook

Рабочий адрес:

```text
https://chistovik-plugin.vercel.app/api/telegram
```

Установить webhook:

```text
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook?url=https://chistovik-plugin.vercel.app/api/telegram&secret_token=<TELEGRAM_WEBHOOK_SECRET>
```

Проверить:

```text
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getWebhookInfo
```

В ответе:

- `url` должен совпадать с адресом Vercel;
- `last_error_message` должно отсутствовать;
- `pending_update_count` обычно равно нулю.

Удалить webhook:

```text
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/deleteWebhook
```

После удаления команды перестанут работать до повторной установки.

Меню команд безопаснее всего обновлять ручным запуском workflow `Configure Telegram menu` в GitHub Actions. Он использует сохранённый секрет и не показывает токен в логах.

Посмотреть текущее меню:

```text
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getMyCommands
```

Очистить меню:

```text
https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/deleteMyCommands
```

После изменения списка команд нужно снова запустить workflow `Configure Telegram menu`.

## Ручной резервный запуск ежедневного отчёта

Основной отчёт отправляет Vercel Cron. Если нужно проверить сообщение немедленно:

1. Открыть репозиторий на GitHub.
2. Перейти в `Actions`.
3. Выбрать workflow `Daily analytics report`.
4. Нажать `Run workflow`.
5. Проверить сообщение в Telegram.

Этот workflow запускается только вручную и не дублирует ежедневное расписание Vercel.

## Как проверить систему вручную

1. Проверить, что `https://chistovik-plugin.vercel.app/api/capture` отвечает и последний Vercel deploy успешен.
2. Открыть `Observability → Queues` и убедиться, что появилась тема `chistovik-analytics` и её обработчик.
3. Запустить плагин в Figma несколько раз.
4. Проверить в PostHog Activity, что появились `plugin_run_started` и финальные события с `analytics_transport = vercel_queue_v1`.
5. Убедиться, что у одной пары начало/результат совпадает `run_id`.
6. Проверить, что в событиях нет текста, названий слоёв и файлов.
7. Проверить `analytics_queue_delivery_count` и `analytics_queue_wait_ms`.
8. Открыть оба дашборда и проверить новую дату `plugin_release`.
9. Написать боту `/today`.
10. Проверить `/speed` и `/errors`.
11. Убедиться, что сообщения ведут на правильные дашборды.

После изменения расчётов или сообщений обязательны:

```bash
npm test
npm run build
git diff --check
```

Тесты приёма и пересылки событий находятся в `scripts/test-analytics-capture.js`, а тесты отчётов и Telegram — в `scripts/test-analytics-report.js`. Оба набора входят в общую команду `npm test`.

## Если отчёт не приходит

Проверять по порядку:

1. Успешен ли последний Vercel deploy.
2. Отвечает ли `/api/capture`.
3. Появляются ли сообщения в `Observability → Queues`.
4. Не растёт ли возраст самого старого сообщения в очереди.
5. Нет ли ошибки обработчика `api/queues/posthog.js` в Vercel logs.
6. Есть ли события в PostHog.
7. Заданы ли все Environment Variables для отчётов и Telegram.
8. Правильно ли установлен Telegram webhook.
9. Совпадает ли `TELEGRAM_CHAT_ID`.
10. Совпадает ли `TELEGRAM_WEBHOOK_SECRET` с секретом webhook.
11. Для ежедневного отчёта — задан ли `CRON_SECRET` и появился ли cron `/api/daily-analytics`.

Telegram endpoint дополнительно защищён:

- принимает команды только через `POST`;
- проверяет секретный заголовок Telegram;
- отвечает только чату с разрешённым `TELEGRAM_CHAT_ID`;
- игнорирует чужие сообщения и неизвестные команды.

## Жёсткие правила дальнейших изменений

- Аналитика не должна менять результат типографики.
- Аналитика не должна задерживать уведомления Figma.
- Ошибки аналитики не показываются пользователю.
- Нельзя отправлять пользовательский текст и названия объектов.
- Нельзя ставить аналитику внутрь отдельных правил типографики без отдельного решения.
- Дашборды и Telegram должны исключать тестовые события.
- При добавлении или переименовании поля нужно одновременно обновить этот документ, PostHog и тесты отчётов.
- Перед публикацией новой версии нужно обновить и проверить `ANALYTICS_PLUGIN_RELEASE`.
