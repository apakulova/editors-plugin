# Правила работы с проектом

## Главное правило общения

- Всегда разговаривать с пользователем простым разговорным языком на русском языке.
- Объяснять всё так, чтобы было понятно обычному человеку без технического образования.
- Не использовать без объяснения технические термины, профессиональный жаргон, сокращения и английские слова.
- Если без специального слова нельзя обойтись, сразу объяснять его смысл простыми словами.
- Правило действует для всех сообщений пользователю: итогов, промежуточных отчётов, вопросов, объяснений и инструкций.
- Это правило важнее стремления дать максимально технический или подробный ответ.

## Визуальная система лендинга

- При любых изменениях в папке `landing` нужно использовать уже существующую визуальную систему сайта.
- Нельзя создавать для отдельного блока или элемента собственные шрифты, размеры текста, насыщенность, межстрочные расстояния, отступы, цвета, скругления, кнопки, подписи и другие стили.
- Новые секции и элементы нужно собирать из уже существующих ролей и общих настроек CSS: верхних подписей, заголовков, основного и вспомогательного текста, кнопок, подписей к иллюстрациям, карточек, отступов и расстояний между элементами.
- Повторяющиеся значения должны задаваться через общие переменные и правила CSS, чтобы их можно было изменить в одном месте для всего сайта.
- Если существующей роли или варианта действительно недостаточно, нельзя добавлять новый без явного предварительного согласования с пользователем.
- После изменений нужно проверять консистентность всей страницы на широком и мобильном экране, а не только изменённого блока.

## Изменения правил типографики

- Любое добавление, изменение или удаление правила типографики должно одновременно отражаться на вкладке `Правила` и в `README.md`.
- До изменения кода нужно показать пользователю дословный текст для вкладки `Правила` и получить явное согласование.
- Нельзя сначала реализовать правило, а текст для вкладки согласовывать после.
- Если новое поведение не нужно показывать на вкладке `Правила`, это исключение тоже необходимо отдельно согласовать с пользователем.
- Нельзя добавлять или менять никакие другие видимые пользователю тексты без прямого предварительного согласования.

## Публичная версия и аналитика

- Публичное название плагина — `Типограф Чистовик`.
- Поддерживается одна версия плагина. Отдельная бета-версия после публичной публикации не ведётся; автор удаляет прежнюю закрытую бету при переходе к публичному плагину.
- Статистика прежней беты и публичной версии остаётся общей в PostHog и Telegram. Не добавлять разделение на бету и публичную версию без отдельного запроса пользователя.

## Дата версии при отправке в GitHub

- Перед каждой отправкой изменений в GitHub через `git push` проверять `ANALYTICS_PLUGIN_RELEASE` в `src/code.ts` и устанавливать текущую дату по Москве в формате `YYYY-MM-DD`.
- Правило действует для любых отправляемых изменений, включая сервер, отчёты и документацию, независимо от публикации плагина в Figma Community.
- Все коммиты и отправки за один московский календарный день используют одну и ту же дату. Не добавлять `.1`, `.2`, номера коммитов, время или другие пометки. Если дата уже сегодняшняя, повторно менять её не нужно.
- При изменении даты обновлять ожидаемое значение в `scripts/test-clean-typography.js`, выполнять `npm run build` и включать обновлённый `dist/code.js` в тот же коммит до отправки в GitHub.
- Изменение даты версии не должно менять правила типографики, пользовательские тексты или другие настройки плагина.

## Переход на точечную обработку текста

- Пока в `scripts/lib/analytics-report.js` указано `POINT_EDITING_PHASE = "baseline"`, нельзя начинать изменения точечной обработки текста до выполнения условий из `docs/development-roadmap.md`.
- При начале первого изменения точечной обработки нужно в том же изменении переключить `POINT_EDITING_PHASE` на `"implementation"`. Это обязательное действие без отдельного напоминания пользователя.
- После переключения ежедневный Telegram-отчёт и команда `/today` не должны показывать временный абзац о готовности к доработкам.
